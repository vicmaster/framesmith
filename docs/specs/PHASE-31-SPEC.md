## 1. SPECIFY

### Problem

framesmith judges an application screen as if it were a marketing page, and cannot see most of what makes it an application. Four failure classes, each confirmed in the baseline or in the code:

1. **The judgment is blind on an app.** The web hit-target floor inspects only the four form controls (`CONTROL_TYPES`, `src/evaluate.ts:1888`); the tappable primitives join the census only when the mobile touch floor is on (`evaluate.ts:1988`, `:1999`). The viewer's detail page has 31 click targets, among them a 17px-tall "← Back" link and 21 spans or divs with click handlers (the inspector tabs, every issue card), none keyboard reachable. All four imported viewer pages scored `usability` 100 with zero findings: buttons, links and tabs import as frame + text, and no rule looks at frames.
2. **Page rules misfire on app screens.** The table detector (`detectTable`, `src/drift.ts:106`) reads the viewer's sidebar project list as a data table, so coverage demands empty and loading variants for the navigation on every page. The type-scale check warns on any adjacent pair below a 1.1 ratio or above 2.0 (`evaluate.ts:572`), which flags the 13/14 and 14/15px steps the viewer uses and its page-title-to-body jumps of 2.4 to 2.7. The accent-consistency tell (`evaluate.ts:1757-1806`) counts the projects' identity dots as four competing accents. The ratio check has no rule id, so no type can switch it off; the ruleset table (`RULESETS`, `src/surfaces.ts`) turns only rule ids on and off, plus the cliché tells it can relax.
3. **There is no app vocabulary.** No link, text input, tab, navigation item, tree row, menu row or inspector row. `button` comes in 32 / 44 / 52 (`BUTTON_HEIGHT`, `src/primitives.ts:8`), so the 24px icon buttons of a dense toolbar cannot be built. There are no overlays: no tooltip, popover, menu, modal or toast, and no layer model (the renderer hard-codes `z-index` 10 for `fixed` and 5 for `sticky`, `src/renderer.ts:1457-1458`). Nothing renders or checks hover, focus, pressed or disabled states. The viewer itself uses three native `confirm()` dialogs (`src/viewer.ts:846`, `:1617`, `:1679`), which a canvas cannot express.
4. **There are no app starting points.** The web set has an app shell (`split-workbench`), `dashboard` and `settings`, but no list-detail, editor-with-inspector or browser layout, and structure resolution assumes exactly two types (`resolveStructure`, `src/structures.ts:1863`, whose fallback is `type === 'web' ? 'mobile' : 'web'`).

The phase's claim: an agent asked for an application screen declares `type: "desktop-app"` once, starts from an app layout built from app primitives, and is judged by rules that know an app. Every click target is measured, the current location is unambiguous, overlays stack in a fixed order, every interactive primitive's focus, active and disabled renders are checked without being drawn by hand, and the misfiring page rules stay quiet.

### The model (Phase 30's, extended)

Phase 30's model holds unchanged: three independent declarations (type, genre, preset), each contributing a ruleset that composes by union; structures split into anatomy and realisation; clickability is a property of primitives, not a flag. This phase adds a third type and two ideas.

**The third type.** `desktop-app` joins `web` and `mobile`. The boundary, stated once in every agent surface: `web` is a page you read and scroll (marketing, docs, content, a pricing page); `desktop-app` is a tool you work in (persistent chrome, panes, dense controls, a current selection), whether it runs in a browser tab or a native window. An admin console, an editor, a file browser and the framesmith viewer are `desktop-app`. A phone screen stays `mobile`.

**Element states and screen states are different things.** An *element state* (hover, focus, pressed, disabled, plus the `active` and `expanded` markers) belongs to one primitive. It is a property of that primitive, drawn by the renderer from state tokens, so the evaluator can compute the relevant states of every interactive primitive analytically, in fast mode, without the agent drawing them. A *screen state* (a menu open, a confirm dialog up, a toast showing) changes what is on screen. It is a variant canvas made with the existing `canvas_add_variant`, holding the open overlay as ordinary nodes, and it is evaluated like any canvas, so every rule (targets included) applies to what the open overlay shows.

**Layers are fixed by kind, and overlays live at the root.** Every overlay primitive belongs to one layer, and the layer fixes its stacking order. The renderer lifts every overlay out of the content tree into one overlay layer after it, whatever its position in the tree, so a menu authored inside a sticky toolbar or a scrolling pane is never clipped or out-stacked. Authors never set a `z-index`. The order follows Atlassian's published ladder: popover and menu, then the modal's scrim, then the modal, then toast, then tooltip.

### Goals

- **A third type** with a window profile, its own ruleset, and a boundary rule agents can apply.
- **Corrections that hold on every type**: the WCAG 2.5.8 spacing exception on the 24px floor, navigation lists that never read as tables, and identity dots that never count as accents.
- **A page rule that can be switched off** because it has a rule id, and a desktop-app ruleset that replaces it.
- **App vocabulary**: links, text inputs, tabs, navigation items, tree rows, menu rows, inspector rows, dividers, and a 24px button with an accessible name.
- **App rules with teeth**: every click target measured, the current location unambiguous, a dense type ladder, consistent table rows, and honest truncation.
- **Panes**: workbench, list-detail, editor-with-inspector and browser layouts, plus desktop-app realisations of dashboard and settings, under the existing pattern gate.
- **Overlays** on a fixed layer ladder, with the single-frame rules that keep them honest.
- **Element states** rendered from tokens and checked analytically on every interactive primitive.
- **Results an agent can read** on a 240-node app screen.
- **Proof by re-run**: the viewer's gallery, detail-with-inspector and archive rebuilt as canvases on this phase, with the overlays it uses, judged by rules that actually ran.

### User stories

- **US1**: As the authoring agent, `canvas_create({ name, type: "desktop-app" })` gives me a 1440×900 artboard, and `generate_design_system` on it gives me a 14px body (13 for `data-dense`), state tokens and a focus-ring color.
- **US2**: As the authoring agent, `apply_structure("editor-inspector")` on a desktop-app canvas stamps a work area and a 70/30 inspector built from `tabs`, `property-row`, `text-input` and `button` primitives.
- **US3**: As the authoring agent, a 20px icon button with no other target inside its 24px circle passes in detailed mode; the same button touching another one is an error naming the spacing exception.
- **US4**: As the authoring agent, a sidebar with two active `nav-item`s warns, and so does one with none; a sectioned sidebar with one active item in one section passes; a sidebar list never asks me for an empty or loading variant.
- **US5**: As the authoring agent, I add a `confirm-delete` variant and drop a `modal` into it. Its scrim, header close button and right-aligned actions come from the primitive, and the evaluator checks that it is the only modal and sits inside the window, without my touching a z-index.
- **US6**: As the authoring agent, a `$focus-ring` that falls below 3:1 against the inspector panel is one error listing every primitive on that panel, though I never drew a focused state.
- **US7**: As the authoring agent, `canvas_evaluate` on a 240-node app screen returns a result I can read in one tool call.
- **US8**: As the reviewing human, the viewer rebuilt on this phase reaches CLEAN with every click target a primitive, including its comment-popover and delete-confirm states, in both themes.

### Terms used below

- **Clickable primitive**: `button`, `link`, `text-input`, `nav-item`, each tab of a `tabs` node, `tree-row`, `menu-row`, `list-row`, the four controls, Phase 30's `tab-bar` items and `nav-bar` actions, and the header close button and `actions` of a `modal` and the `action` of a `toast`. A node of any other type is never a target, even with `state` set.
- **Target circle**: WCAG 2.5.8's test. An undersized target (below 24 in either dimension) passes when a 24px-diameter circle centred on its box intersects no other target's box and no other undersized target's circle. Circles that only touch do not intersect. A target nested inside another target (ancestor or descendant) is not its neighbour. Disabled targets are neither measured nor neighbours.
- **Pane**: a frame with `overflow: "auto"`, a `modal`, a `drawer`, or the root.
- **Navigation group**: within one pane, all `nav-item`s at depth 0 together, wherever their section frames sit; one `tabs` node is its own group.
- **Region**: the nearest pane. Primary buttons inside three or more sibling frames with the same shape hash (`shapeHash`, `src/project-evaluate.ts:80`), such as a grid of cards, are not counted toward their region.
- **Element state**: a primitive's `state` property (FR-G1). **Screen state**: a variant canvas (`canvas_add_variant`).
- **Fast / detailed mode, full tier**: as in Phase 30. Fast mode has no rendered rects; detailed mode adds `computeLayout`.

### Non-goals (explicit scope cuts)

- **No code port of the viewer.** The acceptance proves the design; reimplementing `src/viewer.ts` from it is separate work after this phase.
- **No anchored rendering.** Overlays are positioned by authored `x`/`y`; `anchor` feeds rules only. CSS anchor positioning is not in every browser the viewer serves, and a layout pass before render would make render depend on layout.
- **No keyboard behaviour.** Focus order, Esc, focus trapping and arrow keys need interaction; static checking cannot see them, and the research found no mainstream tool that scores them automatically.
- **No narrow-window behaviour.** The sidebar-to-rail collapse at 641 to 1007px, checks at 1024 and 1280, pane minimum widths and resizable panes are later work; this phase ships one window profile.
- **No "exactly one selected row when the detail pane is populated" rule.** Knowing that a detail pane is populated needs a link between the two panes that the scene graph does not have; FR-C4 flags more than one active row only.
- **No density snapping for hand-built content.** Primitives sit on the ladder by construction, and `data-table-app` carries the Carbon header and toolbar rules; checking that every hand-built control snaps to a rung is not in this phase.
- **No spacing-scale change.** The baseline's off-scale spacing came from an imported page with no design system of its own; a desktop-app canvas built with `generate_design_system` has a declared scale, and the spacing check is right to judge against it.
- **Should-have items left for later**: the command palette, bulk selection, filter-active, inline-edit, undo-toast and rows-selected variants (#14, #15, #18); typed empty and loading states (#19); the destructive-confirm copy rule (#16); an axe-core run (#20); occlusion for arbitrary positioned content and sticky chrome covering a focused node (#21); the inactive-button variant and the "disabled primary with no helper text" advisory (#22); the 1.4.12 text-spacing stress pass (#23); table hygiene (#24); sending the scene graph to the LLM critique (#25). Numbers refer to the research report's prioritized list.
- **Later items**: drag and drop, the AAA focus-appearance check, focus-order heuristics, clutter metrics, shell micro-rules, reflow at 320px, a learned quality model, timing (tooltip delays and toast durations, which no official source gave in milliseconds).
- **No importer work.** The baseline found the importer cannot rebuild an app shell (iframes dropped, pinned and positioned panes flattened, content-free bars lost, a lost width constraint producing a false FRAGILE). Import stays as is; only its report shape changes (FR-A7).
- **No `zIndex` or `role` property, no clickable flag on frames.** Layers come from overlay kinds and clickability from primitives, as Phase 30 settled.
- **No desktop-app rules on web.** Only the corrections (FR-A4, FR-A5, FR-A6, and FR-H3's disabled-text exclusion), the output change (FR-A7), `desktop-app-artboard`, and the new primitives' type-independent renders reach other types.

## 2. CLARIFY  (forks: recommendations)

- **C1: The type name.** *Recommend:* `desktop-app` (Victor's proposal, 2026-11-09). `app` is ambiguous because phone screens are apps too; `desktop` reads as a wide web page. `desktop-app` names a tool you work in at a desktop-class window, whether in a browser or native. The cost is an asymmetry with `mobile`, which is minor.
- **C2: The boundary between `web` and `desktop-app`.** *Recommend:* by what the user does, not where it runs: read and scroll is `web`, work in it is `desktop-app`. The existing web `dashboard` and `settings` stay web realisations, since analytics and account pages exist on marketing sites; their `-app` realisations are the app versions. The `init` GOTCHAS, `GENRE_PARAM_DOC` and the `canvas_set_genre` docstring send editors and admin forms to `genre: "material"` today (`src/index.ts:139`, `:152`, `:2019`); they change to `type: "desktop-app"`, and `material` stays a genre and a preset for the Material style only.
- **C3: Realisation names.** *Recommend:* `<anatomy>-app` (`list-detail-app`), shorter than `-desktop-app`. Agents pass anatomy names and resolution picks the realisation, so the suffix is rarely typed.
- **C4: Element states: a property or variant canvases?** *Recommend:* a property (FR-G1) with analytical checks (FR-H1 to FR-H4). The research proposed state variants, the Storybook pattern. Variants would make the agent draw every state of every control by hand, and the checks would run only where it did. A property lets the renderer draw states from tokens, so every interactive primitive is checked on every canvas. Screen states, where the content changes, stay variants (FR-E3).
- **C5: Overlay positioning.** *Recommend:* authored `x`/`y` in root coordinates, with the renderer lifting overlays into one layer (FR-E1) and `anchor` feeding rules only.
- **C6: Which changes reach `web` and `mobile`.** *Recommend:* only corrections that are wrong everywhere: the spacing exception (WCAG applies on every surface), navigation lists not being tables, and identity dots not being accents; plus the output folding. The accent tell could instead be relaxed by the desktop-app ruleset alone, since `relax` already accepts cliché tells, but identity dots are identity on every type, and relaxing the whole tell would also hide real competing accents on an app.
- **C7: `button` heights and names.** *Recommend:* add `xs` (24) and keep 32 / 44 / 52, since making `md` 32 on desktop-app would make render depend on type (Phase 30 C10). Add `ariaLabel` instead of overloading `label`, which is visible text and decides whether a button is icon-only.
- **C8: `active`, not `current`.** *Recommend:* `active`, matching `TabItem.active` (`src/types.ts:18`), so one word means "this is where you are" across every primitive. The renderer emits `aria-current` for navigation and `aria-selected` for tabs either way.
- **C9: Severities for unvalidated thresholds.** *Recommend:* info. Row heights and column alignment within ±1px, one primary per region, the 4-character truncation floor, more than one toast, and a danger toast are proposals or judgment calls; they inform until the gate or the acceptance run gives evidence that they should block. Header-equals-body (Carbon) and the WCAG-derived rules warn or error.
- **C10: Target checks in fast mode.** *Recommend:* warn, not skip. The spacing exception needs rendered rects, which fast mode does not have. Skipping would let an undersized target through the loop agents actually run; erroring would be wrong whenever the spacing saves it. A blocking warning that names detailed mode keeps the gate honest at the cost of one extra detailed run.
- **C11: Output folding scope.** *Recommend:* fold infos only, from three repeats, never one with a `fix`. Errors and warnings are what agents act on node by node, and `canvas_autofix` emits per-node ops; infos are where the baseline's volume came from.
- **C12: Should-have items pulled in.** *Recommend:* `property-row` (#13) and the primary-count info (#17) come in because the acceptance's inspector and toolbars need them, and `text-input` because the comment popover and the browser filter bar do; `browser`, `dashboard-app` and `settings-app` come in because the acceptance needs `browser` and an app type without its two most common screens would push agents back to the web realisations.

## 5. ANALYZE  (risks and checks)

- **Scope.** Nine slices, more than Phase 30's seven, chosen deliberately (2026-11-09) over a foundation-only phase. Slices E to H cover what the baseline could not test, since the viewer's static pages show no open overlay. If the acceptance run in slice I finds an overlay or state rule misfiring on a correct idiom, the fix lands in slice I with its evidence, as Phase 30 FR-C7 handled mobile.
- **Web verdicts.** FR-A4, FR-A5 and FR-A6 change web behaviour. The padded-row step is kept so lone controls keep their verdicts, but the census grows: a `button` with an explicit `height` below 24 (`buttonHeight`, `src/primitives.ts:56-58`) is measured on web for the first time, and in fast mode an undersized target now warns. The slice A PR lists every existing fixture whose verdict moved and why.
- **Renders on other types.** FR-G1 keeps today's 0.5 disabled opacity unless the canvas has `state` tokens, and FR-B8 uses `$border-strong` only when the token exists, so no existing canvas changes pixels; a canvas that runs `generate_design_system` after this phase gets both tokens and re-renders with them on any type.
- **Fast-mode friction.** FR-A4 and FR-C1 make an undersized target block in fast mode until a detailed run. Primitives are 24 or more by construction, so this lands only on explicit small sizes and hand-made controls, which is where the check matters.
- **Output shape.** FR-A7 changes the shape of folded `info` findings for every caller. A CI gate that counts infos sees fewer entries; the folded entry carries `count`, and the docs state the change. Errors and warnings are untouched.
- **House values.** The smallest text, the prose floor, the `data-dense` body, the type-ladder cap, the sidebar width, the tree indent, the modal widths, the ten-row modal-table line and the disabled-visibility threshold are house values or proposals. They are constants, each in one place, so a better source changes one row.
- **Analytical states versus the renderer.** FR-H1 to FR-H4 compute renders the renderer must actually produce. The slice H render-versus-model test keeps the two from drifting.
- **Overlay layer.** Lifting overlays out of the tree (FR-E1) means an overlay's authored position no longer follows its parent's layout. That is the point (root coordinates), and the docstring says so.
- **Discoverability.** Eight new content primitives, six overlay primitives, a type, rule ids and six structures all land on the agent surfaces in their own slices; `test-discoverability.ts` gains each list as it lands.
