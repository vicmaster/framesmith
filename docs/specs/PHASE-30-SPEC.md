# Phase 30 — The Mobile Surface (v2.4)

> Spec-driven breakdown, borrowing spec-kit's flow: **Specify → Clarify → Plan → Tasks → Analyze**.
> This is a planning artifact, not code. File/symbol references verified against `src/` at commit 1b40732 on 2026-10-31.
> Source: the mobile surface attempt (2026-09-07). One iOS phone screen ("Ridgeline — Today", 390×844, 93 nodes) was built end to end against the published v2.2.0 by following the docs literally. It scored 100/100 and READY TO PRESENT with empty and loading states designed, and not one mobile-specific check ran. The four bug-sized defects it found shipped in PR #232. This spec turns the rest into a surface: a canvas that knows it is a phone screen, a ruleset that judges it as one, the vocabulary to build it, starting points, and a viewer that shows it.

---

## 1. SPECIFY

### Problem

framesmith treats mobile as a screen size, not a surface. An agent asked for an iOS screen today gets a narrow web page, and the evaluator approves it without looking. Four failure classes, each confirmed in the attempt or in the code:

1. **The judgment is blind on a phone.** The touch-target rule inspects only the four form-control types (`CONTROL_TYPES` at `src/evaluate.ts:1785`). The attempt screen had 45 frames, 29 texts, 17 icons and zero control nodes, so the 24px error and the 44px touch-first info both evaluated an empty set and `usability` scored a vacuous 100. Even when a control is found, the phone rule is an `info` (`evaluate.ts:1851`), so it never blocks. Nothing checks safe areas, a body-size floor, or tab-bar sanity.
2. **The declarations are tangled.** Genre (what a screen is for) and preset (what style it uses) share one field, `metadata.provenance.preset` (`src/types.ts:333`), so `apply_preset` silently overwrites a genre stamp (`src/index.ts:1549`) and every preset name (`dark`, `light`, `minimal`) reads as a genre. Separately, `dashboard` is both a genre and a structure name, and a running app had to declare itself a "dashboard" to stop its own distances flagging as fabricated. There is no axis at all for what medium a screen is on.
3. **There is no mobile vocabulary.** No status bar, home indicator, nav bar, tab bar, list row, sheet or button node. No safe-area concept. `position` is `'absolute' | 'relative'` only (`src/types.ts:111`), so a tab bar cannot pin over scrolling content. All 25 structures are desktop shapes; stamping `dashboard` onto a 390px canvas produced a 248px sidebar and a 1192px main column.
4. **The viewer assumes a desktop page.** Gallery thumbnails are hardcoded to a 1440×900 iframe at `scale(0.222)` (`src/viewer.ts:604`, `:756`), so a phone canvas fills about a quarter of its card. The detail view's breakpoint buttons hardcode 390 and 768 (`viewer.ts:1350-1352`) and have no device presentation.

The phase's claim: an agent asked for a phone screen declares `type: "mobile"` once, starts from a mobile archetype built from mobile primitives, and is judged by rules that know a phone. A tap target below 44px on a phone blocks presenting, and the human sees the screen in a device frame in the viewer.

### The model (agreed 2026-09-08, not reopened here)

A canvas carries three independent declarations. They compose; none is nested inside another.

| Axis | Question | Values in this phase | Stored at |
|---|---|---|---|
| **type** | what medium is this on | `web` (default), `mobile` | `metadata.surface.type` (new) |
| **genre** | what is this screen for | `data`, `commerce`, plus legacy aliases | `metadata.provenance.genre` (new; legacy fallback below) |
| **preset** | what style is applied | `dark`, `light`, `material`, `minimal` | `metadata.provenance.preset` (unchanged) |

Each axis value contributes a **ruleset**. Rulesets compose by union: adding a genre adds one ruleset that applies on every type, and adding a type adds one ruleset that applies to every genre.

Structures split **anatomy** from **realisation**. Anatomy is the screen kind, defined once and medium-independent (a settings screen: grouped preferences, each with a label and a control). Realisation is per type (web: a centred column of grouped cards; mobile: grouped list rows). The growth rule every later proposal must pass: adding a type costs one realisation per anatomy it wants, one ruleset and one viewer mode; adding a genre costs one ruleset; adding an anatomy costs one anatomy plus one realisation per type it wants. Nothing is quadratic.

Tappability is a property of primitives, not a flag. A tab item is tappable because it is a tab item, the way `toggle` already carries its own semantics. There is no `tappable: true` property.

### Goals

- **Declarations that do not collide**: genre and preset in separate fields, `data` as the purpose-named genre, and a new `type` axis.
- **A ruleset mechanism that can turn rules on**, not only subtract cliché tells, keyed by any axis.
- **A mobile ruleset with teeth**: 44px targets as an error on every tappable primitive, safe areas respected, a body-size floor, and tab-bar sanity, all blocking.
- **Mobile vocabulary**: device chrome, navigation, list rows, sheets, buttons, and pinned positioning.
- **Mobile starting points** through the anatomy/realisation split.
- **A viewer that presents a phone canvas as a phone.**
- **Proof by re-run**: Ridgeline rebuilt on this phase, judged by rules that actually ran.

### User stories

- **US1** — As the authoring agent, `canvas_create({ name, type: "mobile" })` gives me a 390×844 artboard whose root reserves the safe-area insets, and `generate_design_system` on it gives me a 17px body (16 for the `data-dense` personality).
- **US2** — As the authoring agent, `list_structures` on a mobile canvas shows mobile realisations, and `apply_structure("settings")` on it stamps grouped list rows, not a sidebar.
- **US3** — As the authoring agent, a 32px icon button I built with `button` on a mobile canvas blocks presenting with an error naming the 44px floor; the same button on a web canvas passes.
- **US4** — As the authoring agent, `apply_preset("dark")` on a canvas I stamped `genre: "commerce"` leaves the genre alone.
- **US5** — As the authoring agent, a `tab-bar` pins to the bottom of the phone viewport over scrolling content, reserves the home-indicator inset itself, and is flagged if it has six tabs or an unlabeled one.
- **US6** — As the reviewing human, the gallery shows phone canvases as portrait cards at their real proportions, and the detail view shows them in a device frame with a safe-area overlay I can toggle.
- **US7** — As the reviewing human, Ridgeline rebuilt on this phase reaches CLEAN with every tap target a primitive, in fewer nodes than the 93 it took by hand, in both themes.

### Terms used below

- **Content**: text, icons, controls, `button`, `list-row`, and images narrower than the artboard. Everything else is background.
- **Contentless frame**: a frame or rectangle with no content anywhere beneath it. Fill, border and shadow are allowed.
- **Pinned**: `position: "fixed"`, or `"sticky"` while stuck. "Pinned bottom" means fixed with a `bottom` offset.
- **Reservation**: the space the root keeps clear at an edge. Top reservation = the root's authored top padding + `safeArea.top`. Bottom reservation = authored bottom padding + `safeArea.bottom`. The renderer raises each to at least the height of the `fixed` chrome primitive on that edge when one exists: `status-bar` at the top, `tab-bar` or `home-indicator` at the bottom (FR-D1).
- **Fast / detailed mode**: `canvas_evaluate`'s existing modes. Fast is JSON-only and is what agents run in the loop; detailed adds a Chrome layout pass with real rects.
- **Full tier**: `npm run test:full`, the Chrome-dependent tests.

| **FR-C3** | **Safe areas are respected.** On a `mobile` canvas, content (see Terms) must not sit in the top or bottom inset, and must not end up permanently under a pinned bottom element. ## 2. CLARIFY  (forks — recommendations)

- **C1 — Where the type lives.** *Recommend:* `metadata.surface`, not `provenance`. Provenance records what produced a canvas; type is a declaration of what it is, and it carries a device id that provenance has no reason to know about. Keeping it in metadata also keeps it out of `versionHash`, matching genre.
- **C2 — Does `canvas_set_type` resize the artboard or write `safeArea`?** *Recommend:* no to both. Either would reflow every node the agent placed. FR-C6 warns until the agent resizes deliberately, FR-C3's structural check covers a root without `safeArea`, and `canvas_create({ type })` is where the defaults apply.
- **C3 — `material` as genre or preset.** *Recommend:* both, deliberately. The relaxation is keyed to the preset, so applying the material style relaxes it whatever the genre. `material` also stays a genre with the same relaxation, because the `init` GOTCHAS (`src/index.ts:135`) recommend `genre: "material"` for editors and admin forms and agents follow that advice today. Dropping it from the genre table would change their verdicts, and the duplicate costs one table row.
- **C4 — `data` or `dashboard` as the canonical genre.** *Recommend:* `data`. The genre describes what the numbers are, not the layout, and the attempt showed the layout word pushing a fitness app into the wrong label. `dashboard` stays an alias permanently because stored canvases carry it.
- **C5 — Hand-built frames: gate, advise, or ignore.** *Recommend:* advise (FR-C2). Gating needs a way for a frame to say "I am decorative", which is the tappability flag the model rejected. Ignoring repeats J1's silence. Advising names the fix, and the archetypes make primitives the default path, so the gate covers what the default path produces.
- **C6 — Safe area: rule or renderer.** *Recommend:* the renderer reserves the insets (`root.safeArea`, FR-D1) and the rule polices what can escape the reservation: positioned content, pinned bottom bars, and roots without `safeArea`. This mirrors iOS, where the system insets scroll content automatically and only explicit layout can collide with the bars. Fast mode has no rendered rects and is what agents run in the loop, so the default path must be correct by construction rather than by a check that only detailed mode can make. The modes still disagree on positioned content nested in positioned frames; fast mode says so with an info, and FR-E4 and FR-G1 require both modes.
- **C7 — Tab bar pinned by default.** *Recommend:* yes, `position: "fixed"`, `bottom: 0` unless overridden. A tab bar in flow falls below the fold at artboard height, which is the attempt's V9 finding; making every author remember to pin it re-creates the defect.
- **C8 — Button heights.** *Recommend:* 32 / 44 / 52 on every type, so `md`, the default, passes the 44 floor on a phone. Type-dependent heights would make the render depend on `metadata.surface`, which `versionHash` does not cover (C10). `sm` stays available for pointer surfaces and errors on mobile, which the docstring says.
- **C9 — Short-string skip in stress.** *Recommend:* mobile only. Web stress results stay byte-identical, and the attempt's evidence is mobile-specific.
- **C10 — What the type is allowed to change.** *Recommend:* judgment and presentation only, never the render. The type selects rules, the generator's defaults when it is called, the structures offered, and the viewer frame. Everything that changes pixels (insets, primitive sizes, pinning) lives in the scene graph, where `versionHash` covers it, so a CI verify of a mobile canvas means the same thing it means for a web one.
- **C11 — Undeclared phone-width canvases.** *Recommend:* make them warn (FR-C6). The attempt itself was built with `width: 390` and no type, so leaving that path silent repeats J1 for every agent that reads only the `canvas_create` signature. One explicit call in either direction clears it, so a responsive web page designed at 390 pays one call, not a rule it cannot satisfy.

## 5. ANALYZE  (risks & checks)

- **A declaration is still on the honour system.** FR-C6 closes the silent path (an undeclared phone-width canvas warns), but an agent can still declare `web` explicitly on a phone app screen to avoid the mobile errors, as it could borrow a genre before Phase 29. The remaining mitigation is visibility: the `surface` report is in every evaluate result, and the viewer frames only declared mobile canvases, so a misdeclared phone screen looks wrong to the human. Preventing it outright would need width-based inference, which would make a responsive web page designed at 390 impossible to express.
- **The gate covers primitives, not every pixel.** FR-C1 blocks on every tappable primitive; FR-C2 only advises on hand-built frames. A screen hand-built entirely from frames can still pass with small targets. This is a deliberate trade (C5), and it holds only if the archetypes really are the default path, which is why FR-E4 gates them and FR-G1 counts primitives.
- **Mixed framesmith versions on one repo.** An older framesmith still writes a genre into `preset`. On a canvas this version has migrated, `genre` wins, so an older server's `canvas_set_genre` is ignored here, and an older server reads this version's `preset` as its genre. A repo's collaborators should run the same framesmith minor; GUIDELINES says so.
- **Moving the genre field touches stored data.** The legacy read in FR-A1 is defined negatively (anything that is not a real preset name is a genre), so unknown genres written by the old `canvas_set_genre` survive. Preset names stored by the old `canvas_set_genre` (`material`, `dark`, `light`, `minimal`) are read as presets: `material` keeps its relaxation through the preset ruleset and the others relaxed nothing anyway, so no verdict changes; only `genre.active` goes to null, which is the untangling working. One accepted cost: a `material` stamp written by the old `canvas_set_genre` is now a preset, so `canvas_set_genre(null)` no longer removes its relaxation; applying another preset does.
- **Stress stays advisory and in memory.** A phone canvas that was never stressed is not blocked, and a server restart forgets a FRAGILE verdict. Both are true on web today; FR-C8 does not make them worse, and persisting the verdict is a follow-up, not this phase.
- **Fast and detailed modes can disagree on safe areas.** With `safeArea` on the root the default path is correct in both, and the disagreement narrows to positioned content nested in positioned frames, which fast mode cannot place. Fast mode flags that it cannot see it, detailed is authoritative, and the docs say so in the sentence that introduces the rule.
- **The coverage category does not see list-row lists.** A `feed` realisation's empty state matters as much as a table's, but coverage detection stays table-shaped in this phase (the Phase 29 non-goal on flow-shaped coverage still holds). Stress does treat sibling list-rows as a list (FR-C8).
- **Constants from secondary sources.** Several device values could not be read from Apple's own pages. Slice B re-checks them when it lands the profile table; a wrong inset would make the safe-area rule wrong on every mobile canvas.
- **Seven new node types widen the renderer.** Each is a leaf or a fixed-shape container with its own builder, following the Phase 16 controls. The risk is the `sheet` scrim and `fixed` positioning interacting with `fullPage` capture and `snapshot_layout`; FR-D1's acceptance pins the screenshot case.
- **The pattern gate grows by 30 fast assertions** (six realisations × five themes, Chrome-free), plus six detailed-mode and six stress checks in the full tier, plus one stamp check per `any` component.
- **The proof is the re-run.** If Ridgeline needs a hand-built tab bar, a borrowed type, or a rewritten scaffold to reach CLEAN, the phase is not done.
